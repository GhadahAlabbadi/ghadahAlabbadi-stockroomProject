======================================================================
REQUIRED EXPLANATIONS
======================================================================

----------------------------------------------------------------------
1. Forward versus reverse relationship traversal
----------------------------------------------------------------------
Forward traversal follows a ForeignKey from the model that declares it to the
model it points to, and returns one object: product.category,
order_item.product, order.customer.
Reverse traversal goes the other way, from the referenced model back to the
many side, through the related_name, and returns a related manager that gives
a QuerySet: category.products, customer.orders, order.items,
product.order_items.
Both directions use the same foreign key column (for example
inventory_product.category_id); only the direction of the lookup differs.

----------------------------------------------------------------------
2. Why OrderItem is a model and not only an automatic many-to-many table
----------------------------------------------------------------------
An automatic many-to-many table holds only two foreign keys. An order line
needs more: the quantity, the unit_price at the time of sale, and the rule
that the same product cannot appear twice in one order. These need their own
columns and constraints, so OrderItem is a real model. Order.products still
works as a many-to-many shortcut because it is declared with
through='OrderItem'. The model also makes quantity * unit_price available
for the order totals in the aggregation section.

----------------------------------------------------------------------
3. The difference between get() and filter()
----------------------------------------------------------------------
get() returns exactly one object. It raises DoesNotExist when nothing matches
and MultipleObjectsReturned when several rows match. filter() always returns
a QuerySet, which may be empty, hold one row or hold many rows, and it never
raises for a missing row. Use get() when exactly one row is expected (a
primary key or unique field) and filter() when zero or more rows are fine.

----------------------------------------------------------------------
4. When a QuerySet is evaluated, and why it is called lazy
----------------------------------------------------------------------
A QuerySet is lazy: building it and chaining filter(), exclude() or
order_by() only describes the SQL and does not run it. The database is
queried when the QuerySet is evaluated: by iterating over it, list(), len(),
bool(), printing it, indexing one item, or calling count(), exists() or
first(). After the first evaluation the rows are cached inside that QuerySet,
so using it again does not query again. Laziness lets Django combine all the
chained conditions into one SQL statement and avoids queries whose results
are never used.

EXPLANATIONS
----------------------------------------------------------------------
1. Why aggregate() returns one dictionary:
   aggregate() collapses the whole queryset into a single summary row, so
   there is nothing to attach it to except the query as a whole. Django
   returns it as one dict such as {'total_stock': 462}, keyed by the name
   given in the call. It is a terminal operation: it does not return a
   queryset, so it cannot be filtered or chained afterwards.

2. Why annotate() adds a value to each object or group:
   annotate() keeps the queryset and attaches a calculated attribute to
   every row it returns (for example category.product_count). The result
   is still a queryset, so it can be filtered, ordered and sliced, and
   the calculated value can be used in later filters.

3. What defines the group in the category calculation:
   Category.objects.annotate(Count('products')) groups by Category. Each
   category row is joined to its products through the reverse foreign
   key, and Count counts the joined products for that one category.

4. What defines the group in the order calculations:
   Order.objects.annotate(...) groups by Order. Each order is joined to
   its OrderItem rows. Count('items') counts those rows, and the total
   value multiplies quantity by unit_price on each item row before Sum
   adds them up for that single order.

5. Why the two order annotations are run separately:
   Combining several annotations over the same join can multiply rows and
   inflate the counts and sums. Running them in separate queries keeps
   every number correct and easy to verify.

6. Confirmation against the sample data:
   10 products in total, 8 active; average active price 21.72875; active
   stock 462; categories hold 4, 3 and 3 products; orders hold 2, 2, 2, 1,
   3 and 2 items; order totals 75.48, 58.30, 99.88, 32.50, 86.99 and
   66.70, which add up to 419.85.
